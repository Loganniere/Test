## Situazione di partenza [GiSi, SePa]

Nel Cantone non esiste attualmente alcuna piattaforma centralizzata che permetta ai cittadini di registrare i propri impianti di energia rinnovabile e i propri veicoli elettrici, né di tracciare i dati di produzione energetica e di ricarica dei veicoli.\
Le poche informazioni disponibili sono sparse in fogli Excel personali, applicazioni di terze parti non integrate tra loro, o semplicemente non vengono raccolte.

### Descrizione [GiSi]
La situazione attuale coinvolge:
- **Cittadini privati** che possiedono impianti fotovoltaici, eolici o di cogenerazione sul proprio territorio
- **Proprietari di veicoli elettrici** (auto, moto, scooter, biciclette a pedalata assistita) che non dispongono di strumenti unificati per il monitoraggio
- **Uffici comunali e distrettuali** che non hanno visibilità sull'adozione delle energie rinnovabili nel proprio territorio

Non esiste alcun software specifico in uso per questa gestione. I dati vengono eventualmente annotati su carta o su fogli di calcolo non standardizzati.

### Costi attuali [GiSi]
- Nessun costo informatico diretto, poiché non esiste un sistema digitale
- Costo indiretto stimato in termini di tempo per la gestione manuale dei dati: circa 2-3 ore/mese per utente attivo
- Nessuna possibilità di aggregazione dei dati a livello territoriale: costo opportunità elevato per la pianificazione energetica comunale

### Volumi e frequenze [SePa]
- Stima utenti potenziali nel Cantone: 500-2000 famiglie con impianti rinnovabili
- Frequenza di inserimento dati attesa: almeno 1 volta a settimana per utente attivo
- Dati storici attualmente non disponibili in formato digitale strutturato

### Tecnologie in uso [MuLu, GiSi]
- Nessun software specifico per la gestione energetica domestica
- Fogli di calcolo (Microsoft Excel / LibreOffice Calc) per le annotazioni manuali
- Nessun database centralizzato
- Nessuna infrastruttura server dedicata
- Non è prevista ripresa di dati da sistemi precedenti: si parte da zero

## Progetto

La piattaforma **Auto Solari** è un'applicazione web che consente ai cittadini di registrare i propri impianti di energia rinnovabile e i propri veicoli elettrici, tracciare la produzione energetica e i consumi di ricarica, e consultare statistiche aggregate per comune e distretto.

### Scopo
Il mandante richiede una piattaforma web che:
- Permetta la registrazione e la gestione dei propri impianti rinnovabili (fotovoltaico, eolico, cogenerazione)
- Permetta la registrazione e la gestione dei propri veicoli elettrici (auto, moto, scooter, bicicletta)
- Consenta il tracciamento giornaliero delle ricariche effettuate e dell'energia prodotta
- Offra statistiche personali e pubbliche aggregate per territorio (comune/distretto)
- Garantisca la privacy: nessun dato personale visibile pubblicamente


### Obiettivi
Obiettivi formulati in modalità SMART:

1. **Registrazione utenti**: entro fine M2, almeno il 100% delle funzionalità di registrazione/login devono essere operative e sicure (password con hash Werkzeug)
2. **Gestione impianti e veicoli**: entro fine M2, gli utenti possono aggiungere, modificare ed eliminare impianti (fotovoltaico/eolico/cogenerazione) e veicoli (auto/moto/scooter/bicicletta)
3. **Tracciamento dati**: entro fine M3, gli utenti possono registrare ricariche e produzioni anche su range di date, con distribuzione automatica dei kWh giornalieri
4. **Statistiche**: entro fine M3, le statistiche pubbliche mostrano dati aggregati per comune/distretto con filtri per giorno/mese/anno
5. **Import dati**: entro fine M3, è disponibile un'interfaccia di importazione massiva tramite JSON per le ricariche

### Volumi e frequenze
- **Utenti attesi**: 100–2000 utenti registrati nel primo anno
- **Impianti per utente**: mediamente 1–3 impianti
- **Veicoli per utente**: mediamente 1–2 veicoli
- **Ricariche**: 1–7 inserimenti a settimana per utente attivo
- **Produzioni**: 1–30 record al mese per impianto (inseribili come range)
- **Crescita del DB**: stimata ~50 MB/anno con 500 utenti attivi


### Proposte di possibili soluzioni

#### Soluzione 1 — Applicazione web custom (scelta adottata)
Sviluppo ex-novo di una web app in Python/Flask con database SQLite.\
Controllo totale su funzionalità, schema dati e UI. Nessuna dipendenza da licenze esterne.\
Ideale per un progetto scolastico con team di 3 persone.

#### Soluzione 2 — CMS con plugin (es. WordPress + plugin energetico)
Utilizzo di un CMS esistente con plugin per la gestione energetica.\
Meno flessibile, difficile da adattare ai requisiti specifici, overhead di gestione elevato.

#### Soluzione 3 — SaaS esistente (es. SolarEdge, Victron)
Utilizzo di piattaforme SaaS commerciali già esistenti.\
Non personalizzabili per le esigenze specifiche del mandante; costi ricorrenti elevati; dati ospitati su server esterni.


### Criteri di scelta della soluzione
È stata scelta la **Soluzione 1** perché:
- Permette il controllo completo sui dati (privacy GDPR)
- Stack tecnologico (Python/Flask/SQLite) noto al team
- Nessun costo di licenza
- Facilmente estendibile in futuro (es. aggiunta di nuovi tipi di impianto o veicolo)
- Deployment semplice: un solo file Python + DB SQLite


### Sicurezza
- **Autenticazione**: hash delle password con `werkzeug.security.generate_password_hash` (PBKDF2-SHA256)
- **Sessioni**: Flask session con `SECRET_KEY` configurabile tramite variabile d'ambiente (`os.environ.get("SECRET_KEY", ...)`)
- **Autorizzazione**: decorator `@login_required` su tutte le route private; ogni operazione CRUD verifica che la risorsa appartenga all'utente loggato (`WHERE user_id = ?`)
- **SQL Injection**: tutte le query usano parametri `?` (prepared statements SQLite)
- **GDPR**: le statistiche pubbliche non espongono dati personali; solo aggregati per comune/distretto
- **Foreign Keys**: `PRAGMA foreign_keys = ON` — eliminazione a cascata per mantenere l'integrità referenziale


### Ripresa dati
Non è prevista alcuna ripresa di dati da sistemi precedenti. Il database viene inizializzato da zero all'avvio con `init_db()` che esegue `schema.sql`.

## Realizzazione

### Make or buy?
È stata scelta la soluzione **Make** (sviluppo ex-novo) perché:
- I requisiti sono specifici e non coperti da soluzioni SaaS esistenti a costo zero
- Il team possiede le competenze per sviluppare in Python/Flask
- Il controllo completo dei dati è un requisito fondamentale (GDPR, hosting locale)
- La soluzione deve essere facilmente manutenibile dal mandante nel tempo


### Metodologia
**Incrementale**: il progetto è suddiviso in 4 milestone, ognuna delle quali rilascia un insieme di funzionalità operative e verificabili. Non si è scelto Agile puro (sprint) per la ridotta dimensione del team (3 persone) e la durata breve del progetto (~2 mesi).


### Tecnologie

| Tecnologia | Alternativa valutata | Motivazione scelta |

| Python 3.12 + Flask 3.x | Django, FastAPI | Flask è leggero, adatto a progetti medio-piccoli, noto al team |
| SQLite | PostgreSQL, MySQL | Nessun server DB separato; sufficiente per i volumi previsti |
| Werkzeug (hash password) | PyJWT, passlib | Incluso in Flask, standard per hashing password |

### ER
Il database è composto da 5 tabelle:

- **users**: dati anagrafici dell'utente, email univoca, hash password, comune e distretto
- **impianti**: impianti rinnovabili dell'utente (fotovoltaico/eolico/cogenerazione), kW installati, data installazione. FK → users
- **veicoli**: veicoli elettrici dell'utente (auto/moto/scooter/bicicletta), marca, modello, capacità batteria, km totali. FK → users
- **ricariche**: sessioni di ricarica per veicolo, con data, ora inizio/fine, kWh erogati, km percorsi. FK → veicoli, users
- **produzioni**: produzioni energetiche giornaliere per impianto, kWh prodotti. FK → impianti, users

![ER](./allegati/img/5.6_ER.jpg)

#### DDL
```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    nome TEXT NOT NULL,
    cognome TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    via TEXT,
    comune TEXT NOT NULL,
    distretto TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS impianti (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    tipo TEXT NOT NULL CHECK(tipo IN ('fotovoltaico', 'eolico', 'cogenerazione')),
    kw_installati REAL NOT NULL,
    data_installazione DATE NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS veicoli (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    tipo TEXT NOT NULL CHECK(tipo IN ('auto', 'moto', 'scooter', 'bicicletta')),
    marca TEXT,
    modello TEXT,
    capacita_batteria REAL NOT NULL,
    km_totali REAL DEFAULT 0,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS ricariche (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    veicolo_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    data DATE NOT NULL,
    ora_inizio TIME,
    ora_fine TIME,
    kw_erogati REAL NOT NULL,
    km_percorsi REAL DEFAULT 0,
    FOREIGN KEY (veicolo_id) REFERENCES veicoli(id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS produzioni (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    impianto_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    data DATE NOT NULL,
    kw_prodotti REAL NOT NULL,
    FOREIGN KEY (impianto_id) REFERENCES impianti(id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

#### DML
Esempi di query significative utilizzate nell'applicazione:

```sql
-- Statistiche pubbliche: consumo per comune nel mese corrente
SELECT u.comune as label, SUM(r.kw_erogati) as totale, COUNT(DISTINCT r.user_id) as n_utenti
FROM ricariche r JOIN users u ON r.user_id = u.id
WHERE r.data >= '2026-02-01'
GROUP BY u.comune
ORDER BY totale DESC;

-- Dashboard privata: consumo mensile utente
SELECT SUM(kw_erogati)
FROM ricariche
WHERE user_id = 1 AND data >= '2026-02-01';

-- Ultime 5 ricariche con dettaglio veicolo
SELECT r.*, v.tipo, v.marca, v.modello
FROM ricariche r JOIN veicoli v ON r.veicolo_id = v.id
WHERE r.user_id = 1
ORDER BY r.data DESC
LIMIT 5;
```

Algoritmo di rilievo — distribuzione ricarica su range di date (`app.py`):
```python
d_start = date.fromisoformat(data_inizio)
d_end = date.fromisoformat(data_fine)
delta = (d_end - d_start).days + 1
kw_giorno = kw / delta
km_giorno = km / delta

current = d_start
while current <= d_end:
    db.execute(
        "INSERT INTO ricariche (...) VALUES (?, ?, ?, ?, ?, ?, ?)",
        (veicolo_id, uid, current.isoformat(), ora_inizio, ora_fine,
         round(kw_giorno, 4), round(km_giorno, 4)),
    )
    current += timedelta(days=1)
```
Questo permette all'utente di inserire, ad esempio, "100 kWh consumati in 10 giorni" e il sistema crea automaticamente 10 record da 10 kWh/giorno.

## Conclusioni

### Scelte
Il progetto ha raggiunto tutti gli obiettivi prefissati nelle 4 milestone pianificate.\
Le scelte tecnologiche (Python/Flask/SQLite) si sono rivelate appropriate per la dimensione del progetto: deployment semplice, nessuna dipendenza esterna costosa, codice mantenibile.\
La scelta di supportare l'inserimento su range di date ha significativamente migliorato l'usabilità per gli utenti che non inseriscono i dati quotidianamente.\
L'import JSON è un valore aggiunto che permette l'integrazione futura con sistemi di domotica o wallbox di ricarica che esportano dati in formato strutturato.

### Altri elementi
**Possibili evoluzioni future:**
- Aggiunta di un pannello amministratore per la gestione utenti
- API REST per l'integrazione con app mobile o dispositivi IoT
- Notifiche email periodiche con riepilogo energetico
- Grafici interattivi con Chart.js o D3.js
- Supporto per più cantoni/regioni con filtri geografici avanzati
- Migrazione da SQLite a PostgreSQL per ambienti con molti utenti concorrenti
